# 构建和发布 Windows 候选版本

推送应用提交和对应版本标签后，在 `main` 上运行 Release，填写版本、已验收的中文标题与发布说明。默认生成候选，也可以显式勾选 `prepare_candidate`。快速检查通过后，Windows 测试与打包并行。打包封存的同一份产物供四组 E2E 和各安装方式的隔离测试使用。

工作流成功后，在运行摘要查看升级路径、下载候选并验收。用户批准当前候选后，在新一次 Release 运行中勾选 `publish_release`，填写同一版本及候选运行 ID（`source_run_id`），沿用候选固化的中文标题和说明。发布作业会检查来源、附件、两份证明与上一个正式版本的基线，并原样发布候选。候选包保留 7 天，验收凭证保留 90 天。包已过期、标签提交变化或正式基线变化时，需要重新生成候选。发布失败可重跑失败作业，或从同一候选恢复。

需要在给定标签上演练时使用 `validate_only`。候选、演练和正式发布三种模式互斥。已有旧格式恢复产物按原规则校验。

## 失败诊断

- 优先查看运行摘要和首个失败步骤。网络或 runner 瞬态故障使用 Actions 的“重新运行失败的作业”。重试会继续使用成功打包的 artifact，修改源码或工作流则需要启动新运行。
- 四组 E2E 报告按构建 ID 和尝试号汇总。已有外部夹具跳过清单之外的跳过会阻止签发验收凭证。需要合并 Blob 报告时，可以使用 `npx playwright merge-reports --reporter html <目录>`。
- 每个安装场景保存独立的报告和日志。报告记录下载方法、SHA-256、应用重启、健康确认和保留数据的验证结果。所有报告必须匹配同一候选。对比耗时时记录 runner 排队、打包、最慢 E2E、最慢安装场景及发布上传时间。

## 全量与增量验收

v2.2.10 正式更新清单只向旧客户端提供全量包。2.2.8、2.2.9 的 MSI 在经过应用内全量更新后可能拥有增量基线，但缺少可写的 Squirrel 临时目录。目标版本的修复在旧客户端完成升级后才能生效。只有从 v2.2.10 或更新版本生成的增量才可重新写入后续正式更新清单。

发布仍生成并核验原始 Squirrel 增量。产品升级场景使用正式清单测试从 v2.2.8、v2.2.9 的 Setup 和 MSI 升级，MSI 另覆盖实际上由 2.2.6 安装并升级的历史状态。候选客户端分别运行全量和增量到隔离测试后继版，核对实际使用的包，增量场景发生全量回退会失败。后继包只供测试，在候选目录之外生成。MSI 产品测试使用验证过的普通用户令牌，并检查安装根目录可写且父目录不可写。ZIP 和禁用更新器的 MSI 通过手动覆盖升级验证。

从 v2.2.11 起，当前正式版的 Setup、有更新基线的 MSI，以及刚安装的 MSI 分别验证实际选包。候选升到隔离后继版时，测试代理模拟 GitHub API 限流，并确认客户端通过官方下载入口取得清单后完成升级。
